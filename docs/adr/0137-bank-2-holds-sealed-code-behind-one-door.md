# 0137. Bank 2 holds sealed code behind one door

- **Status:** Proposed
- **Deciders:** owner (bank-2 design decisions 1–8, 2026-10-11), firmware

## Context
Bank 1's firmware area (0x08020000–0x080FFFFF, 917,504 B) is nearly full: the shipping build leaves about 50 KB, ORBIT less, and TAPE alone costs about 46 KB (ADR 0132 took it out for alpha). The STM32H753 has a second 1 MB flash bank that nothing uses. Its sectors 4–7 (0x08180000+) are bootloader 1.09's slots, which the stock bootloader jumps to on a held button; sectors 0–3 (0x08100000–0x0817FFFF, 512 KB) are free. Calling code in flash that may be erased, torn, half-written or from another build would fault or worse, so the way in has to make a wrong call impossible, not unlikely (spec `docs/superpowers/specs/2026-10-11-bank2-design.md` §§ 1–2).

## Decision
- **One link, two regions.** One `cargo build` places `.bank2` at 0x08100000 (`BANK2`, 512 KB, `bank2.x`); `just bank2-split` cuts it out as `<out>.bk2` and writes bank 1 as `<out>.bin` with `-R .bank2`. Bank 2 is S0–S3 only: nothing writes, erases or maps for write 0x08180000+, the option bytes, bank 1's flash registers, or bank or mass erase.
- **A 256-byte header** at 0x08100000 (`chimera-image`): magic `CHIMERA2`, format 1, body length and CRC-32, door offset, seal, version, and a commit word (`0xB2C0_FFEE` ×8) programmed last.
- **The seal** is the first 8 bytes of the body's SHA-256, computed on the host after the link (`chimera-utils bank2-seal`) and patched into bank 1's `BANK2_SEAL`. Equal bodies mean every cross-reference is right for either bank 1, so the seal is an exact compatibility key. A build with no seal step keeps `UNSEALED` and never opens bank 2.
- **The judge** (`chimera_image::judge`, pure, host-tested) reads in order: commit word (`Empty`, `Torn`), magic (`Foreign`), format (`Format`), bounds (`Corrupt`), seal (`Stale`), body CRC (`Corrupt`), else `Good`. A read the flash refuses is `Unreadable`, reported `corrupt`.
- **One door, at 0x08100100** (`DOOR_ADDR`, right after the header): a table of function pointers and data. A `Door` exists only from `Door::open`, a `Good` verdict over live bank-2 reads (`Bank2Memory`) for this build's seal; `DOOR_CELL.open` takes it and refuses any other address; bank 1 reaches the table only inside `DOOR_CELL.with`. A post-link check (`door-check`) fails the build if any bank-1 relocation resolves into bank 2.
- **The boot judges bank 2** right after the MPU is set (`chimera_board::bank2::boot_judge`). On `Good` it opens the door and checks it once (`probe(1) == 43`, the table's first and last bytes); anything less closes it and reports `corrupt`.
- **The MPU** keeps region 0 (DMA). Region 1 is 0x08100000, 1 MB, no access, XN, strongly-ordered, for good. Region 2 is 0x08100000, 512 KB, in one of four states: `Closed` (off), `Read` (read-only, XN, Normal non-cacheable: the boot's state and the one a closed bank 2 stays in, so the console's `flash` can still read S0, and every read sees the flash itself), `Write` (read-write, XN, strongly-ordered) and `Open` (read-only, executable, Normal write-through). Into `Open`, the whole D-cache is cleaned and invalidated by set/way and the whole I-cache invalidated first; every switch ends DSB, ISB. No cache operation names a bank-2 address, so none can raise MemManage on a no-access or read-only region. The console's `flash` no longer reads 0x08180000.
- **A double ECC error read from S0-S3 costs one reset, never a loop.** The HardFault handler (BusFault is never enabled, so the flash's bus error escalates to it) checks for a bus fault (CFSR), FLASH_SR2.DBECCERR and FLASH_ECC_FA2R's word inside S0-S3 (`chimera_image::bank2_ecc_fault`), writes `BANK2_BAD` to RTC_BKP14R, reads it back and resets; anything else halts as before. The boot reads BKP14R before any bank-2 read (`boot_action`): a mark erases S0 (erase clears its ECC), then is cleared, and bank 2 is `Empty` by construction, not read that boot. A failed erase keeps the mark and leaves bank 2 unread and closed (`bank2 ecc erase failed <why>`). After a clean judge the boot clears SR2's flags, so a stale DBECCERR (a speculative read's) can't turn a later, unrelated bus fault into a reset.
- **The boot installs a staged image itself** (owner decision 2): after the card mounts and before the project loads, if flash isn't `Good` for this build, the first of `/CHIMERA/SYSTEM/BANK2.BK2` and up to 32 root `*.BK2` (a dropped file's short name, `CHIMER~1.BK2`; the root is listed and read, never written) that judges `Good` (`find_staged`, `pick_staged`), behind DON'T POWER OFF. Others are ignored silently; no file is renamed or deleted, and a boot with flash `Good` reads none. BKP14R holds `BANK2_INSTALLING` meanwhile; a fault during it keeps that mark, and the next boot erases S0 and installs nothing, so a word that faults on every install costs one more reset per boot, never a loop. Worst case per power-on: the judge faults (reset), the next boot erases, installs and faults again (reset), the next erases and reads nothing, and PART 1 comes up: two extra resets, bounded. A failed install leaves the staged file for the next boot.
- **What testers see:** `status` adds `bank2 open <version> seal=<16 hex>`, `bank2 stale have <version>`, `bank2 ecc erase failed <why>` or `bank2 empty|torn|foreign|corrupt|format <n>|unsealed`; SETTINGS › SYSTEM › ABOUT reads `OK` when open, else `NEEDS UPDATE` (owner decision 8).
- **The only writer is Chimera's own**, from the UI loop or the boot, from `/CHIMERA/SYSTEM/BANK2.BK2` staged by the console's `put` or, at boot, a `.BK2` dropped in the card root: erase S0 first, body, header, read back, commit word last. Never ROM DFU, never the stock bootloader.
- **`put` parses one SYSTEM path,** `/CHIMERA/SYSTEM/BANK2.BK2`. ADR 0092's "SYSTEM never parses" no longer holds for it; every other SYSTEM name still refuses.

## Alternatives considered
- **Data only in bank 2:** about 13 KB to move today, and the UI's fonts must stay in bank 1 to say `NEEDS UPDATE`.
- **Two images with a stable ABI:** `extern "C"` for every shared type, a second `core`/`libm` in bank 2, and Rust has no stable ABI for the engines' state.
- **ROM DFU or the stock bootloader as the writer:** the 2026-10-07 ROM DFU erase of bank 2 hung; the stock bootloader writes bank 1 only, and with a large `.bin` erases its own sector.
- **A version number instead of a seal:** two builds of one version can differ in any address bank 2 calls.
- **SHA-256 on the device:** the seal is a header field compared exactly, and the body's CRC proves the bytes; about 2 KB of SHA saved.

## Consequences
- **An update is one action** (amended 2026-10-14, owner; supersedes spec decision 1's two steps; amended 2026-10-15 to the release as shipped). A release ships one firmware, the ORBIT build, as loose files: `CHIMERA.BIN` and the `CHIMERA.BK2` sealed for it, beside `factory-v1.zip` and `SHA256SUMS`. The tester flashes the `.bin` as before and copies the `.bk2` to the card root; the new firmware's first boot installs it. There is no zip a variant and no console tool for testers; `chimera-usb.py update <bin> <bk2>` (stage the `.bk2` under the running firmware, DFU the `.bin`, then `status` must show the seal open) is the developer's `just flash` and the gates' route. Firmware from before bank 2 can't stage: the tool flashes first, then puts and installs. A firmware change that leaves bank 2's bytes alone keeps its seal: no reinstall.
- Bank 1 pays for the judge, the MPU states and the status text: about 2.8 KB.
- A stray load or fetch in bank 2 faults with a clear address instead of reading erased or torn flash; anything in 0x08180000+ always does.
- A double ECC error on a bank-2 read resets once and erases S0; an image staged on the card then reinstalls at that boot. RTC_BKP14R is bank 2's: nothing else writes it.
